3.3 案例 3: 从模糊需求到项目计划

Powered by impress.js
Ver. 2602

### 案例说明 - **案例目标**: 先把模糊需求变成可执行计划 - **任务内容**: 规划并可选实现一个学习任务看板 - **输入材料**: `docs/` 中 4 份需求文件 - **最终输出**: 规划文档, 可选 MVP 原型 - **课堂重点**: Agent 不只是代码生成器
### 教学目的 - **理解节奏**: 先澄清需求, 再拆任务, 最后写代码 - **训练能力**: 识别冲突, 排优先级, 设计验收 - **观察差异**: 聊天常会直接开写, Agent 更适合先读资料 - **形成判断**: 好实现来自好规划, 不来自长代码
### Trae 的课堂映射 - **聊天生成**: 直接问方案或代码 - **Agent 生成**: 让 AI 先读 `docs/`, 再产出计划 - **Skill + Agent**: 先写规划规则, 再允许实现 MVP - **平台定位**: Trae 强调理解需求并推进任务链路 - **本课做法**: 用同一需求观察 AI 会不会先规划
### 初始材料与验收 - **需求简述**: `product_brief.md` - **利益相关者**: `stakeholder_notes.md` - **项目约束**: `constraints.md` - **验收标准**: `acceptance_criteria.md` - **底线要求**: 不用框架, 用 `localStorage`, 页面可直接打开
### 方式一: 聊天生成 - **第 1 步**: 直接把需求扔给聊天窗口 - **第 2 步**: 要它给方案, 结构, 代码 - **第 3 步**: 观察它是否先处理冲突与优先级 - **第 4 步**: 记录它有没有跳过验收计划 - **课堂观察**: 聊天最容易一上来就写代码
### 聊天生成要看什么 - **需求冲突**: 会不会同时满足过多想法 - **功能取舍**: 有没有区分必须做与可以缓做 - **规划质量**: 有没有任务拆解与测试计划 - **代码风险**: 是否一次生成过长, 难以维护 - **常见问题**: 方案看似完整, 其实缺少验证边界
### 方式二: Agent 生成 - **第 1 步**: 打开案例目录, 明确先不要急着写代码 - **第 2 步**: 让 Agent 先读完全部 `docs/` - **第 3 步**: 先生成 `output/` 下的规划文档 - **第 4 步**: 再按优先级实现 `project/` 中的 MVP - **课堂观察**: Agent 更适合先读后做
### Agent 生成要看什么 - **阅读完整**: 是否真的看了 4 份需求材料 - **冲突处理**: 是否识别教师, 学生, 助教意见差异 - **优先级**: 是否先做添加, 删除, 状态, 存储 - **验收意识**: 会不会主动写测试计划与风险列表 - **人类职责**: 决定哪些功能要暂缓
### 方式三: Skill + Agent - **第 1 步**: 先写 `mini-project-planning-skill` - **第 2 步**: 规定必须先规划, 后实现 - **第 3 步**: 规定必须区分 must, should, could - **第 4 步**: 规定实现后按验收标准自查 - **课堂观察**: Skill 把项目助理式工作固定下来
### 这个 Skill 至少写什么 - **读取范围**: 必须读完全部需求文件 - **冲突识别**: 单列不一致意见与取舍理由 - **规划输出**: 需求摘要, 任务拆解, 数据结构, 测试计划 - **实现边界**: 先做 MVP, 不强求一次做全 - **最终说明**: 交代已实现, 未实现, 以及原因
### 课堂检查点 - **是否先规划**: 有没有先出文档再写代码 - **是否会取舍**: 有没有机械堆功能 - **是否守约束**: 有没有引入框架或外部依赖 - **是否可验收**: 页面刷新后数据是否保留 - **是否可复盘**: 人和 Agent 各做了什么判断
### 教师补充说明 - **关键转变**: 让 AI 先做项目助理, 再做代码助手 - **Trae 价值**: 适合展示多文档阅读后的连续执行 - **Skill 价值**: 让规划步骤不再被跳过 - **课堂提问**: 哪些需求值得保留到第二版 - **收束问题**: 如果只能做 30 分钟, 先保哪 5 项
