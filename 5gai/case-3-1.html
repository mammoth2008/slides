3.3 案例 1: Markdown 转网页

### 案例说明 - **案例目标**: 用同一份材料, 对比三种做法 - **任务内容**: 把课程笔记转成静态网页 - **输入材料**: `source/` 与 `requirements/` - **最终输出**: `index.html`, `style.css`, `app.js`, `README.md` - **课堂重点**: 从 "生成代码" 走向 "完成任务"
### 教学目的 - **理解差异**: 聊天, Agent, Skill 不只是入口不同 - **观察重点**: 是否真正读完全部材料 - **训练能力**: 结构整理, 多文件输出, 结果验收 - **形成判断**: 不是谁更快, 而是谁更稳
### Trae 的课堂映射 - **聊天生成**: 用对话面板直接给需求 - **Agent 生成**: 让 AI 读取目录并执行任务 - **Skill + Agent**: 先写 `SKILL.md`, 再交给 Agent - **平台定位**: Trae 强调理解需求, 调动工具, 推进任务 - **本课做法**: 用同一材料比较三种工作方式
### 初始材料与验收 - **核心文件**: `ai_programming_notes.md` - **补充文件**: `glossary.md` - **约束文件**: `webpage_requirements.md` - **关键检查**: 目录, 术语卡片, 练习区, TODO 区 - **底线要求**: 页面离线可打开, 不依赖外网
### 方式一: 聊天生成 - **第 1 步**: 手动复制主要 Markdown 内容 - **第 2 步**: 再补网页要求与输出文件清单 - **第 3 步**: 让 AI 一次性生成 4 个文件 - **第 4 步**: 手动保存到 `output/` - **课堂观察**: 材料越长, 漏项风险越高
### 聊天生成要看什么 - **标题层级**: AI 会不会自行修正混乱层级 - **TODO 处理**: 是否集中到待补充区域 - **术语来源**: 是否真的用了 `glossary.md` - **练习保留**: 表格与课堂任务有没有丢失 - **常见问题**: 一次输出太长, 文件拆分不稳定
### 方式二: Agent 生成 - **第 1 步**: 打开案例目录, 不手贴全文 - **第 2 步**: 提示 Agent 先读 `source/` 与 `requirements/` - **第 3 步**: 让它直接生成 `output/` 下的 4 个文件 - **第 4 步**: 要求它自查目录链接与 TODO 区 - **课堂观察**: Agent 更像在完成一个小项目
### Agent 生成要看什么 - **读取行为**: 它有没有先读文件再动手 - **结构能力**: 会不会主动整理导航与卡片 - **多文件输出**: 文件命名是否稳定 - **自查能力**: 会不会检查链接, 标题, 乱码 - **人类职责**: 审核内容边界, 不让它编造理论
### 方式三: Skill + Agent - **第 1 步**: 先写 `SKILL.md` - **第 2 步**: 明确适用场景, 输入, 输出, 禁止项 - **第 3 步**: 写清标题整理, TODO 归并, 术语抽取 - **第 4 步**: 写清自查清单后再执行 - **课堂观察**: Skill 把经验变成可复用流程
### 这个 Skill 至少写什么 - **何时使用**: 处理教学 Markdown 转网页时启用 - **如何读取**: 先读 `source/`, 再读 `requirements/` - **如何整理**: 修正标题层级, 保留重要内容 - **如何抽取**: 把术语解释整理成概念卡片 - **如何检查**: 对照输出文件与验收标准逐项核对
### 课堂检查点 - **是否漏读**: `glossary.md` 有没有被真正使用 - **是否越界**: 有没有编造课程中没有的工具 - **是否可用**: `index.html` 能否直接离线打开 - **是否可讲**: 页面是否适合投影与学生自学 - **是否可复做**: 下一组同学能否复现同样流程
### 教师补充说明 - **同材对比**: 三种方式必须用同一份原始材料 - **不要只看颜值**: 重点是完整性与稳定性 - **Trae 价值**: 它适合展示从对话到执行的过渡 - **Skill 价值**: 不是更炫, 而是更可重复 - **收束问题**: 哪一步最需要人工判断
