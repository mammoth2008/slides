# Mindmap 与 Markdown 源文件对照分析

## 概述

mindmap HTML 中的 JSON 结构与 md 源文件的结构**不是一一对应**的。mindmap 的节点层级（h1/h2/h3/li）是由**内容语义**决定的，而不是由 md 的 `###` / `####` / `- ` 决定的。

---

## 关键发现

### 1. `####` 图片标题：被跳过，不进 mindmap

**规则**：md 中 `#### 图片标题` 是图片的说明文字，不是章节标题。在 mindmap 中完全**跳过**，不生成任何节点。

**证据**：`cciot-2-1.md` 中大量 `####`（如第 10 行的 `#### Virtualization`），但 `mindmap-2-1.html` 的 JSON 中找不到对应的节点。

**结论**：脚本解析 md 时，**必须跳过**所有 `####` 行。

---

### 2. mindmap 的结构分层

mindmap 中有四种节点类型：

| tag | 含义 | 对应 md 什么 |
|-----|------|-------------|
| `h1` | 根节点（整张图的核心主题） | md 第 1 行章节编号 |
| `h2` | 一级分支（主要知识模块） | md 中语义上属于同一主题的一组 h3 |
| `h3` | 二级分支（子主题/分组标题） | md 中连续的、有共同前缀的 h2 |
| `li` | 叶子节点（具体知识点） | md 中的 `-` 列表项 |

**注意**：`h2` / `h3` / `li` 在 mindmap 中的层级**不是** md 中 `###` / `####` / `- ` 的直接映射。

---

### 3. 连续同前缀 h2 → mindmap 中的 h3

**规则**：md 中标题**完全相同或前缀相同**的连续 `###` 行，在 mindmap 中被合并为一个 `h3` 分支（作为某个 `h2` 的子节点）。

**证据**：GAI-3-2 的 mindmap 中：

```
h2: 课堂练习
  h3: V1: 用一句 Prompt 生成初始页面  ← md 中是独立的 h2
  h3: V2: 用对话方式增加筛选功能     ← md 中是独立的 h2
  h3: V3: 让 AI 协助拆分项目结构      ← md 中是独立的 h2
```

三个独立的 `### V1:` / `### V2:` / `### V3:` 在 mindmap 中被合并到 `### 课堂练习` 这个虚拟 h2 下，作为三个 h3。

**分组依据**：
- 相同前缀：`V1:`, `V2:`, `V3:` → 合并为 h3
- 同义主题：相关子主题 → 合并到父主题 h2 下

---

### 4. 图片标题相邻的 h2 → 无子 h3，只有 li

**证据**：`cciot-2-1.md` 中，`### 虚拟化 Virtualization` 后面紧跟两个图片标题 `#### Virtualization` 和 `#### Hypervisor Types`。mindmap 中该 h2 的 children 全部是 `li`，没有 h3。

**结论**：当一个 h2 后面只有图片说明（无列表项）时，mindmap 中该 h2 直接带 `li` 叶子节点，不产生中间层级。

---

### 5. 重复标题的处理：合并而非去重

**证据**：`cciot-2-1.md` 中有两个完全相同的 `### VMware 网络模式`（第 89 行和第 94 行），中间隔着一段列表项内容。mindmap 中只有一个 `VMware 网络模式` 分支。

**规则**：跨内容段落的重复标题，mindmap 中**合并**为一个分支，内容合并。

---

## 脚本设计建议

### 解析顺序

1. **第 0 步**：读取 md，解析所有行，过滤掉 `####`（图片说明）
2. **第 1 步**：识别 `###` 段落（每个 `###` 到下一个 `###` 或文件末尾之间的一组内容）
3. **第 2 步**：将连续的、标题前缀相同的 `###` 段落识别为**一组**，生成一个虚拟 h2，下属各段变成 h3
4. **第 3 步**：每个段落内的 `-` 列表项 → li
5. **第 4 步**：输出 mindmap JSON

### 两种分组模式

**模式 A**：各 `###` 独立成 h2（内容不相关时）

```
md:
### A
  - li1
  - li2
### B
  - li3

mindmap:
h2: A → li1, li2
h2: B → li3
```

**模式 B**：连续同前缀 `###` 合并为一个虚拟 h2（V1/V2/V3 等）

```
md:
### V1: 用一句 Prompt 生成初始页面
  - ...
### V2: 用对话方式增加筛选功能
  - ...
### V3: 让 AI 协助拆分项目结构
  - ...

mindmap:
h2: 课堂练习  ← 虚拟分组
  h3: V1: ...
  h3: V2: ...
  h3: V3: ...
```

### 分组识别规则（初步）

1. **标题完全相同**：跨段落重复 → 合并为同一 h2
2. **标题前缀相同**（前 N 字相同，N ≥ 4）：如 `V1:` 和 `V2:` → 合并为虚拟 h2
3. **标题不同但内容相关**：如"虚拟化"和"虚拟机软件" → 各自独立 h2
4. **一个 `###` 后紧跟图片说明** → 该 `###` 直接带 li，不生成中间 h3 层

## 新发现

### 6. payload 标签是元数据，与 JSON 嵌套层级无关

mindmap JSON 中的 `payload.tag` 字段记录的是**原始 md 中的标题级别**（`h1`/`h2`/`h3`），不是当前节点在 mindmap 树中的嵌套深度。

**证据**：`mindmap-2-2.html` 中：
```
h2 (payload: tag="h2", lines="2,3")           ← 原始 md h2
  h3 (payload: tag="h3", lines="4,5")        ← 原始 md h3
    li (payload: tag="li", lines="5,6")      ← 原始 md li
  h3 (payload: tag="h3", lines="12,13")
    li ...
h2 (payload: tag="h2", lines="19,20")
  h3 (payload: tag="h3", lines="21,22")      ← md 中没有 h3！为何有 h3？
    li ...
```

问题：`GAI-2-2` 的 md 中没有 `####` 标题，但 mindmap JSON 中存在 `payload.tag="h3"` 的节点。payload 计算可能有误，或 mindmap 作者添加了原始 md 中没有的中间层级。

**结论**：mindmap 真正的层级结构只看 JSON 的 children 嵌套，不管 payload tag。payload 是辅助信息，**不可作为层级映射的依据**。

---

### 7. JSON 嵌套层级总为 h1 → h2 → h3 → li（四层）

所有 mindmap 的 JSON 树都遵循这一固定嵌套：

```
h1 (payload h1)
  h2 (payload h1 或 h2)
    h3 (payload h2 或 h3)
      li (payload li)
```

**规律**：
- mindmap **第一层** children = h2 节点（payload 可能是 h1 或 h2）
- mindmap **第二层** children = h3 节点（payload 可能是 h2 或 h3）
- mindmap **第三层** children = li 节点

没有 h4 或更深的层级。payload 中的"h4"等在现有 mindmap 中未出现。

---

### 8. 当 `###` 后有多个分组主题时 → h2 下有多个 h3

**证据**：`GAI-2-2` 的 "图片生成" section（md 第 19 行起），mindmap 中：

```
h2: 图片生成
  h3: 图片生成
    li: 控制一张图的内容和风格 ...
    li: 从描述走向可控生成 ...
    li: 从单句提示词走向工作流
  h3: 产品地图
    li: Midjourney ...
    ...
  h3: 工作流工具
    li: WebUI ...
    ...
```

md 中第 19 行是 `### 图片生成`，第 36 行是 `### 产品地图`，第 45 行是 `### 工作流工具`——三个独立的 `###`。mindmap 中它们变成了一个 h2（图片生成）下的三个 h3。

**规则**：连续的、属于同一大类主题的 `###` 段落，在 mindmap 中被合并为一个 h2，下属各段变成 h3。

---

### 9. h3 内容与父 h2 内容相同的特例

**证据**：`mindmap-2-2.html` 中，"图片生成" h2 下第一个 h3 的 content 也是"图片生成"（与父节点同名）。这不是冗余，而是表示：**该 h2 下的第一个列表项组**归入一个与父节点同名的 h3。

```
h2: 图片生成
  h3: 图片生成        ← 与父同名 = 第一个 li 组
    li: 控制一张图的内容和风格 ...
    li: 从描述走向可控生成 ...
    li: 从单句提示词走向工作流
  h3: 产品地图        ← 新的 h3 = 下一个 md h2
    li: ...
```

## 脚本设计建议（修订版）

### 分组识别算法

```
输入: md 中的所有 ### 段落（每个 ### 到下一个 ### 之间的内容）
输出: mindmap JSON 树

1. 过滤 ####（图片说明）
2. 从上到下扫描 ### 段落:
   - 若当前段落与前一个段落: 标题前缀相同（≥4字相同）→ 合并到同一 h2
   - 若当前段落与前一个段落: 标题前缀不同 → 判断是否属于前一个大主题
     - 是 → 作为新 h3 加入前一个 h2
     - 否 → 开一个新的 h2
3. 每个 h2 下的连续段落 → 各变为 h3
4. 每个 h3 内的 - 条目 → li
```

### 关键挑战

**如何判断"是否属于前一个大主题"？** 这需要语义识别，当前无法自动完成。可能的方案：

1. **前缀规则**：当前后两个 ### 标题前缀相同（≥4字）→ 属于同一 h2
2. **行距规则**：两个 ### 之间的距离（行数）< 某个阈值 → 可能相关
3. **人工标记**：在 md 中添加注释（如 `<!-- group: 课堂练习 -->`）让脚本识别
4. **先验分组**：课程制作者先确定好分组结构，md 按分组组织

## 新发现（2026-04）

### 10. 真实 mindmap 与手动创建 mindmap 的区别

**重要警告**：mindmap-3-2.html 是**手动创建**的，不代表标准转换规则。真实转换规则应从课程作者制作的原始 mindmap（mindmap-2-1/mindmap-2-2 等）中总结。

**已验证的真实模式**（来自 CCIOT-2-1 和 GAI-2-2）：

| 模式 | 证据 |
|------|------|
| `####` 完全跳过 | cciot-2-1.md 中大量 `#### Virtualization`，mindmap 中无对应节点 |
| 连续同前缀 `###` 合并为虚拟 h2 | GAI-3-2 中 V1/V2/V3 合并为"课堂练习"h2 |
| payload tag ≠ JSON 嵌套深度 | GAI-2-2 中无 md h3 但 mindmap 有 h3 payload |
| h3 与父 h2 同名 = 第一个列表项组 | GAI-2-2 "图片生成" h3 = h2 下的第一个 li 组 |
| JSON 固定四层嵌套 | h1→h2→h3→li，payload tag 不可作为层级依据 |

**手动创建的 mindmap**（如 mindmap-3-2）可能不反映真实规则，需谨慎参考。

---

### 11. payload lines 的计算规则

**规则**：payload 中 `lines` 字段指向**原始 md 中该节点对应内容的起止行号**。

**li 节点的 lines**：
- 若 li 内容直接来自单个 md 列表项 → lines = 该行范围
- 若 li 内容由多个 md 行合并 → lines = 合并范围的起止行
- 例：GAI-3-2 中 V2 的一个 li（"观察: 增量更新还是整体重写"），其 lines="59,63"，对应 md 中整个"V2 观察要点"段落（第 59-64 行），而非单独的观察条目

**h2/h3 节点的 lines**：
- 对于 h2：指向 md 中对应 `###` 标题的行范围（通常是两个连续行号）
- 对于 h3：同样指向 md `###` 标题行
- **例外**：当 mindmap 手动创建时，lines 可能不精确

**payload tag 计算**：
- tag 记录的是**原始 md 中的标题级别**（`h1`/`h2`/`h3`），而非当前节点在 mindmap 树中的深度
- GAI-2-2 中 mindmap h2 下的 h3 payload tag 来自原始 md 的 `###`（h2），说明分组节点的 payload tag 继承自被合并节点的原始级别
- 计算方法（推测）：
  1. 原始 md 中每行分配一个标签（h1/h2/h3/li/####）
  2. mindmap 生成树时，同组内的节点保留原始标签
  3. payload tag = 该节点内容在原始 md 中的主要级别

---

### 12. payload 行号不对应 mindmap 内容位置

**关键发现**：mindmap 树中各节点的顺序**不一定**与 md 行号顺序一致。payload 的 `lines` 只告诉你这段内容原本在 md 的哪些行，**不**告诉你它在 mindmap 中的位置。

**验证方法**（以 GAI-2-2 为例）：
1. 从 mindmap JSON 中提取所有 h2 节点及其 payload lines
2. 按 lines[0] 排序 → 得到 md 中的实际顺序
3. 该顺序与 mindmap h2 的 children 顺序对比，发现存在不一致
4. 这说明 mindmap 分组/合并操作会打乱原始行号顺序

**实用结论**：
- `lines` 字段只用于**溯源**（这段内容来自 md 哪行），不用于确定 mindmap 位置
- 脚本生成 mindmap 时，应按语义分组而非按行号排序

---

### 13. mindmap 是快照，行号反映生成时的 md 版本

**关键发现**：mindmap HTML 中的 payload `lines` 指向的是 mindmap **生成时**的 md 文件行号，而非当前 md 文件的行号。

**证据**：
- `mindmap-1-2` 中 h3 "ELIZA" 的 lines=11,12
- 当前 `gai-1-2.md` 中 `### ELIZA` 在第 14 行
- 差异正好是 3 行：第 11 行的图片和第 12 行的图片标题是后来插入的
- 说明 Eliza 图片是在 mindmap 生成**之后**才添加到 md 的

**含义**：
- mindmap 记录的是生成时的 md 快照
- 同一 mindmap 中不同节点的 lines 可能对应**不同版本的 md**（如果 md 被多次编辑）
- payload lines **不可用于**自动化脚本校验 md 与 mindmap 的对应关系
- 只能用于理解 mindmap 生成时的原始 md 结构

**实用结论**：
- 重新生成 mindmap 时，必须使用当前 md 文件
- 如果 mindmap 行号与当前 md 不一致，说明 md 已被修改，需要重新生成 mindmap

### 14. h2 + 同名 h3 模式（GAI-1-2/GAI-2-2 验证）

**已验证规律**：当一个 h2 节点包含多个 h3 子节点时，**第一个 h3 的 content 通常与父 h2 的 content 相同**。

**证据 GAI-1-2**：
```
h2: 深度生成模型
  h3: 深度生成模型    ← 同名，第一个 li 组
    li: 利用神经网络从数据中提取特征 ...
  h3: 潜在空间
    li: ...
```

**证据 GAI-2-2**：
```
h2: 图片生成
  h3: 图片生成        ← 同名
    li: 控制一张图的内容和风格 ...
  h3: 产品地图
    li: ...
```

**规则**：这个同名 h3 表示：父 h2 下的**第一组列表项**（来自 md 中的第一个 `###` 段落）归入一个与父节点同名的 h3。这是 mindmap 的语义分组特征。

---

### 15. h2 直接带 li（无 h3）的场景

**规律**：当一个 h2 节点对应的 md 内容只有列表项而没有多个语义分组时，mindmap 中该 h2 直接带 `li` 叶子，不产生中间 h3 层。

**证据 GAI-1-2**：
- `h2: 扩散 (Diffusion) 模型` → 直接带 4 个 li，无 h3 子节点
- 对应 md：`### 扩散 (Diffusion) 模型` 后面只有列表项，无子分组

**对比**：`h2: 深度生成模型` → 有 4 个 h3 子节点（对应 md 中有 4 个子节）

**判断规则**：
- md 中一个 `###` 下有多个同主题的子 `###` → h2 带多个 h3
- md 中一个 `###` 下只有列表项 → h2 直接带 li

### 16. 自动化生成 mindmap 的核心算法（草案）

基于以上所有规律，自动化生成 mindmap 的算法草案：

```
输入: md 文件（所有 ### 段落和列表项）
输出: mindmap JSON

1. 解析 md，过滤 ####（图片说明）
2. 将 md 分段：每个 ### 到下一个 ### 之间的内容为一个段落
3. 确定 h2 节点（主要知识模块）：
   a. 相邻同前缀 ###（如 V1:/V2:/V3:）→ 合并为虚拟 h2
   b. 相邻同主题 ###（如 VAEs/GANs 都在"深度生成"下）→ 合并
   c. 单独一个 ### → 独立 h2
4. 对于每个 h2：
   a. 如果下属有多个子主题 ### → h2 下创建多个 h3
      其中第一个 h3 与 h2 同名，表示第一组列表项
   b. 如果下属只有列表项 → h2 直接带 li
5. 每个 h3/段落内的 - 列表项 → li
6. 输出 JSON，payload tag = 原始 md 中的级别，lines = md 行号
```

**关键挑战**：判断哪些相邻 `###` 应合并（模式 B）vs 各自独立（模式 A）。目前只能基于：
- 标题前缀相同（V1/V2/V3）
- 主题语义相关（由课程制作者确定）
- 人工分组标记（未来可引入 md 注释）

### 17. "观察要点" 类 slide 的特殊处理（GAI-3-2 参考）

mindmap-3-2（手动创建）展示了"V 系列"练习的结构处理方式：

```
h2: 课堂练习
  h3: V1: 用一句 Prompt 生成初始页面
    li: 描述需求, 不加额外约束
    li: 记录 AI 原始输出
    li: 评估: 差距在哪里          ← V1 观察要点被并入
  h3: V2: 用对话方式增加筛选功能
    li: 每次 Prompt 只提一个要求  ← 来自 Prompt 示例 slide
    li: 记录每次修改范围
    li: 观察: 增量更新还是整体重写 ← 来自 V2 观察要点
  h3: V3: 让 AI 协助拆分项目结构
    li: 区分数据层, 视图层, 交互层
    li: 观察: 哪些拆分合理, 哪些过度设计
    li: 思考: 人机协作中谁做架构决策
```

**观察**：
- "观察要点"标题被跳过，不产生独立 h3
- 观察要点的内容条目被拆散，重组到父级 Vn h3 下的 li 中
- "Prompt 示例"的内容也被整合进 h3 的 li 列表
- 最终每个 Vx h3 呈现：Prompt 逻辑 + 操作方法 + 观察视角
