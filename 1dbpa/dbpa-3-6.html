DROP VIEW
DBPA | CH03 | 3.6 | 3.6.1

删除视图：按依赖情况决定处理方式

先盘点下游依赖，再确认所用 DBMS 的删除行为

情况处理思路需要向所用 DBMS 确认
没有下游依赖直接删除定义可用 IF EXISTS
存在下游视图先显式处理依赖再删除不把 CASCADE 当自动清理
产品支持 CASCADE先确认会连带删除哪些对象不要假定 DBMS 会自动清理
基本表被删除视图可能失效定义清理需显式检查

视图消解：用保存的 SELECT 替换视图名

替换后得到基本表查询；它不另存结果，也不固定 DBMS 执行计划

用户查询中的视图名　＋　保存的 SELECT→替换并合并列、表与条件→基本表查询→结果

检查

检查确认视图和来源对象的确存在

重写

用视图的 SELECT 替换视图名，再合并要查询的列、来源表和两边的筛选条件

执行

交给 DBMS 选择执行计划；这是流程描述，不是固定执行顺序

平均值条件放到 HAVING

Gavg 在分组后才得到，因此条件不能放进分组前的 WHERE

SQL
01

09CREATE VIEW S_GradeAVG(Sno, Gavg) AS
SELECT Sno, AVG(Grade) FROM SC GROUP BY Sno;

SELECT Sno, Gavg FROM S_GradeAVG
WHERE Gavg >= 90;

SELECT Sno, AVG(Grade) AS Gavg
FROM SC GROUP BY Sno
HAVING AVG(Grade) >= 90;
Takeaway

Gavg 在分组后产生，条件要放进 HAVING

UPDATE BOUNDARY

不同视图形态的回写边界

能否唯一定位源行列，与目标 DBMS 是否支持，是两个问题

视图形态回写判断
行列子集通常可以唯一定位基本表元组
表达式／计算列改计算结果通常不能唯一决定源列怎样改
多表连接部分简单情形可能支持；须结合键、操作和 DBMS 判断
聚集与分组通常没有唯一的底层改法
Takeaway

实际使用前需要查看产品手册
