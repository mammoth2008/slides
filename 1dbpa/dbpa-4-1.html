10/16
ROLES
DBPA | CH04 | 4.1 | 4.2

DAC：有授权资格的人决定谁能做什么

对象所有者或持有转授权资格的人，可以把指定对象操作授给别人

谁决定

DBA、对象属主，或拥有该权限及 WITH GRANT OPTION 的用户可以作出授权决定

决定什么

决定用户对对象可以执行哪些具体操作

可能出错

权限可能沿转授权继续传播，也可能授给了不该获得的人

Takeaway

DAC 解决谁能做什么，但不替代完整性检查；DAC 通过后仍需按模型检查 MAC

11/16
DAC
DBPA | CH04 | 4.1 | 4.2

MAC：系统再比较主体许可证与客体密级

即使某人拿到了普通授权，只要读写不满足密级规则，系统仍会拒绝

概念含义例子
主体发起访问用户或进程
客体被访问表、视图或文件
密级标记主体许可证／客体密级S／C（判断见 c3）
Takeaway

MAC 由系统按密级强制执行，不能靠普通 GRANT 转授；读写结果由主体许可证级别和客体密级共同决定

12/16
MAC LABELS
DBPA | CH04 | 4.1 | 4.2

MAC 防止高密级信息写入低密级对象

设密级顺序为 TS >= S >= C >= P

规则条件结果
读取主体许可证级别 ≥ 客体密级才允许读取
写入主体许可证级别 ≤ 客体密级才允许写入
双重检查DAC 与 MAC 都通过才允许访问
主体许可证客体密级读取写入
SC允许拒绝
CS拒绝允许
SS允许允许
Takeaway

S 级主体读取 C 级对象后，可能带着 S 级信息；禁止它再写入 C 级对象，是为了避免高密级内容向下流动。上表仍以 DAC 通过为前提；MAC 不是普通 MySQL GRANT 的已验证功能

许可证是 S，读取 C 没问题，为什么写回 C 反而被拒绝？

MAC RULES
DBPA | CH04 | 4.1

四个请求：查什么、结果怎样、还缺什么

先写主体、操作、对象和授权来源，再判结果；审计另记时间、账号和结果

请求一：学生查 Student

学生已登录但请求整表 SELECT：检查对象权限和行窗口；登录成功本身不足以放行

请求二：教师改成绩

T17 请求 UPDATE SC.Grade：检查有效角色、列级权限和数据完整性；三者回答不同问题

请求三：U7 继续插入

U5 的授权被回收后 U7 仍请求 INSERT SC：追踪传播链、回收规则和是否存在独立授权路径

请求四：S 写入 C

即使 DAC 已允许，主体 S 写入客体 C 仍被 MAC 拒绝，以阻止高密级信息向下流动
