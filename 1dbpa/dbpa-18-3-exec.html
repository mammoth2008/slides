第 1 题 / 共 7 题 · 匹配题

将系统取向与典型设计重点匹配

正确答案：区块链 → 在多主体或开放环境中强调改动可检测、历史可追溯和共同验证；关系数据库 → 在明确管理边界内强调事务并发、查询能力、响应和吞吐；许可链 → 用受控身份和共同治理缩小开放网络的协调范围；分布式数据库 → 用复制、分片和协调协议处理受控环境中的故障与扩展

这些是典型取向而非绝对二分，具体安全性和性能取决于信任假设、架构和实现

将四类数据或证据与它们主要回答的问题匹配

正确答案：链式交易历史 → 网络按什么顺序接受了哪些操作；节点状态数据库 → 执行已接受历史后当前可查询什么；关系表 → 业务数据按什么模式组织并支持哪些事务操作；数据库 WAL 与审计记录 → 系统如何恢复更新并追踪受控环境中的操作证据

链上区块不等于业务当前表，也不等于数据库 WAL；对象相似不表示事务边界和治理责任相同

第 3 题 / 共 7 题 · 匹配题

将数据库技术引入区块链时的主要收益与边界匹配

正确答案：分片 → 把状态和交易分区以并行处理，但会引入跨片协调；STM 或 MVCC → 提高无冲突交易并发度，但冲突检测、回滚和确定执行仍有成本；索引 → 加快状态定位和查询，但需要维护空间并保持与已接受状态一致；Bloom 过滤器 → 用紧凑结构快速排除大量不存在项，但可能出现假阳性

每项技术只缓解特定瓶颈，不能取消共识、验证和一致状态责任

Bloom 过滤器对某个键返回“不存在”时，可以怎样解释？

正确答案：在当前过滤器假设成立时，该键一定不在集合中

Bloom 过滤器没有假阴性但可能有假阳性；返回“可能存在”仍需访问真实数据验证，且过滤器不负责交易合法性

把链式日志和数字签名引入数据库审计后，能够增强哪些能力？

正确答案：检测审计记录被插入、删除或改写造成的链断裂、验证某条记录由持有相应密钥的主体签署、为审计证据提供顺序和来源线索、在密钥管理和日志锚定可靠时提高事后核验能力

可验证审计增强证据完整性，但不保证输入真实，也不替代用于故障恢复的数据页、备份和 WAL

第 6 题 / 共 7 题 · 多选题

一个单一受信组织经营的高吞吐订单系统，需要复杂 SQL、频繁更正和分钟级恢复。哪些判断更合理？

正确答案：关系数据库通常应作为核心交易系统、用事务、复制、备份和时间点恢复满足可靠性需求、若需防篡改审计，可额外采用签名或哈希链保护审计日志、数据更正和隐私要求需要在保留策略中明确处理

信任边界集中且查询与恢复要求高时，数据库加可验证审计往往比全量上链更匹配目标

第 7 题 / 共 7 题 · 回想题

多家机构需要共同确认少量关键凭证，但各自仍要运行高吞吐业务和复杂查询。怎样设计融合边界？

对照答案：各机构可用关系数据库处理本地事务、查询、备份和恢复，只把跨机构必须共同确认的凭证摘要、状态转换或审计锚点提交到许可链；链上协议定义身份、提交和治理，链下数据库保存详细业务状态。还需明确链上链下的一致性、失败补偿、隐私、密钥、索引和证据回查流程，避免把同一事实的责任留在两个系统之间
