将需求压力与较直接的架构机制匹配

正确答案：单机容量和吞吐不足 → 分片与横向扩展；节点故障仍需继续服务 → 副本与故障切换；事务与分析都要求较新数据 → HTAP；训练和推理需要数据库内数据治理与计算 → DB4AI；同一业务包含关系、图、文档和时序对象 → 多模型协作

每种机制只缓解部分压力，还要承担协调、隔离、恢复或治理成本

将分布式组件与职责匹配

正确答案：分片 → 决定数据被划分到哪些节点；路由 → 根据分片规则把请求送到目标节点并聚合结果；副本 → 保存同一分片的数据拷贝；共识 → 在故障假设下协调副本接受顺序或状态

分片解决规模，副本解决冗余，共识解决副本协调，路由连接请求与数据位置

第 3 题 / 共 7 题 · 多选题

硬件变化可能怎样改变数据库成本中心？

正确答案：大内存减少部分磁盘读取但放大持久化与恢复设计的重要性、NVM 缩小内存与存储延迟差距但仍需考虑耐久和一致性、高速网络降低通信成本但不会消除网络分区和协调、多核推动并行执行但会增加共享状态协调

硬件变化重新分配代价，不会让事务、故障和治理问题消失

第 4 题 / 共 7 题 · 匹配题

将云数据库形态与主要边界匹配

正确答案：传统托管数据库 → 云平台代管实例和运维，但计算与存储扩展常较耦合；云原生数据库 → 更强调计算、存储和服务组件解耦与按需扩缩

解耦提高资源弹性，也会增加网络、元数据、缓存一致和故障恢复复杂度

用“需求—硬件—架构—取舍”分析未来数据库方向时按步骤排列

  1. 明确规模、热点、故障、实时或异构需求
  2. 评价协调、恢复、隔离、成本和治理代价
  3. 识别网络、多核、内存和存储等硬件条件
  4. 选择分片、副本、云原生、HTAP 或多模型等机制

正确答案：明确规模、热点、故障、实时或异构需求 → 识别网络、多核、内存和存储等硬件条件 → 选择分片、副本、云原生、HTAP 或多模型等机制 → 评价协调、恢复、隔离、成本和治理代价

三副本分片系统失去一个节点时，为什么“有副本”仍不足以直接保证可以提交？

对照答案：还要看剩余副本是否满足协议要求的法定人数、故障节点是否影响领导者或路由、复制进度是否足够新，以及网络是否把集群分割。副本提供冗余，共识或协调协议决定哪些节点组合可以接受新状态；恢复后还需补齐落后副本并处理重配置成本
